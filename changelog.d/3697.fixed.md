`chelis prove`'s fuzz tier pairs binders from *different* magnitude classes
once it has finished proposing each binder's own edge inputs, so it no longer
reports a passing empirical verdict for a multi-binder property that fails at
a pair of representable inputs its guards admit. A property claiming `x / y`
is finite for positive `x` and `y` previously passed at every sample count;
the tier now refutes it with a large `x` and a subnormal `y`.

Each binder's edge inputs were indexed by the run's attempt ordinal, which is
shared, so binders with equal ranges took the same input at every attempt and
only ever met on the diagonal of the grid of possible pairs. The attempts
after a binder's edge inputs are exhausted now propose a cell of an odometer
over each binder's extremal classes instead of drawing at random: its
interval's extremes, the values nearest zero from each side, a zero its guards
admit, and the input nearest `1.0` in magnitude. Those are the binder's own
edge inputs, so no new input is proposed and the guards still admit every pair
the tier reports.

The edge inputs themselves are proposed exactly as before, at one per attempt,
so a property refuted by one is refuted at the same sample count it was. What
the pairings consume is up to 256 of the attempts that would otherwise have
drawn at random from the narrow proposal window, which is 36 of them for a
two-binder property at the default sample count. A single-binder property is
unaffected, and the pairings do not depend on the seed, so a property refuted
at one is refuted under every seed.

A property whose `where` clause orders one binder against another keeps the
previous behaviour exactly and gets no pairings. Such a binder's inputs are
derived from the other binder's value, so proposing a paired input anywhere in
the property would change which inputs the dependent binder is offered at all,
and a property that previously failed could start passing.

See [#3697](https://github.com/Chelis-Lang/chelis/issues/3697).
