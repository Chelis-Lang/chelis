A numeric trap in a compiled program writes its message to stderr and exits
with status 1, the status `chelis eval` uses, as [04-NUM-10] requires.
Previously the binary aborted (SIGABRT, shell status 134) after printing the
message. See [#3107](https://github.com/Chelis-Lang/chelis/issues/3107).

The language failures that `chelis eval` and compiled programs both report
now end both lanes the same way, with status 1 and identical text from one
shared rendering:
- Elementwise operands whose runtime shapes disagree trap
  `numeric trap: domain in <op> at i64` after a line naming each operand's
  shape. This applies to arithmetic, comparisons, logical operations and
  `where`, as spec/04 section 4.7 requires; compiled programs used to abort
  with a different message.
- A sparse index outside its axis traps `Domain` in `gather`, `scatter`,
  `scatter_replace` or `scatter_elements` ([05-SPARSE-1]). The evaluator used
  to panic or print a non-trap message.
- `reshape` with a negative runtime target extent, or with a target whose
  element count disagrees with the input, traps `Domain` in `reshape`.
- A List `index` outside the List, and a negative `take` or `skip` count, report
  the same message in both lanes.
- `matmul` operands whose shared or batch axis disagrees at run time trap
  `numeric trap: domain in matmul at i64` on both lanes, after a line naming
  each operand as written. Previously the evaluator printed a non-trap
  message, and compiled programs named the internal `mul` the lowering
  produces.
- `grad`, `vmap`, and named-axis evaluation pass a numeric trap through
  unchanged rather than prefixing it with `host runtime ... evaluation
  failed:`.
