## Exact condition for a future target-only exception

For an ordinary PR, the exception could apply to a status-`M` root file that maps to the **same one eligible target in base and candidate Cargo metadata**. Do not initially opt in additions, deletions, renames, source-path/feature changes, or ambiguous targets. Evaluate *all* changed paths first. A product-source path, manifest/lockfile, shared helper or fixture, reviewed package path rule, required-package rule, or unknown shared path must keep its present selection. Targeted rebases retain their full required reverse-dependency frontier. The changed root's own target remains required (or needs the current exact-head standing-coverage receipt if standing).

The further condition is a closed reader graph, evaluated on both base and candidate: every target or required CI job that can compile, embed, inspect, enumerate, or read that root must be recorded. Every reader target must be either the root's own target or already executed on the same candidate as a standing/independently required target. An unclassified read, dynamic path, reader introduced by the candidate, or missing receipt must fall back to the full package. If a nonstanding sibling is known, target-only is false; select that sibling as required or retain expansion. The graph must include Rust `mod`/`#[path]`/`include*`, build scripts, Python oracles and scripts, inventories, fixture traversals, and workflow commands. A string search is useful for finding edges but is not a fail-closed proof of their absence. The current planner validates configuration and receipt shape, but does not provide that reader proof. An explicit authoring rule that test roots are private except declared readers, backed by an executable check that constrains all relevant read sites and rejects undecidable readers, would be the needed contract change. If the checker cannot establish that complete closure, retain expansion.

## Opportunity in the downloaded three-week file list

The 2026-09-08–29 `target/pr_files_3weeks.json` has 531 created PRs: 263 touched the CLI `tests/` tree, 256 touched a root `.rs` test target, and **219 of those 256 also touched some crate `src/` path**. These 219 must retain source-driven expansion. Of the remaining 37, three touched `Cargo.toml` or `Cargo.lock`, leaving 34. Applying this head's package/path rules to the other paths in those 34 PRs finds ten that independently select CLI (for example #2753's shared helper and #2161's `tests/common/mod.rs`), leaving **at most 24 PRs, 4.5% of the 531**, with a possible selection change. Six of the 34 changed only CLI root files; five were single-root modifications. This is a path-based upper bound, not a certified saving: **the defensible range today is 0–24 PRs**, pending reader proofs and exact candidate plans. The file lists are final/current PR files, not necessarily the file set or head selected by any earlier expansion run; #2753's sampled run head `bb1a5ed…` differs from the inventory's `768a27b…`. No runtime or dollar saving follows from these counts alone.

## Crate split and next PR

Splitting tests into several crates changes package labels and which package the planner expands; it does not by itself reduce the per-shard workspace-product build or establish file-reader isolation. A test-only crate would also lose automatic same-package access to `CARGO_BIN_EXE_chelis`, used by existing tests, unless binary provisioning and command contracts change. `chelis-cli` is binary-only, so new test crates cannot simply depend on its library. Ordinary PR planning does not add reverse dependencies for product-source edits, so moving tests could silently omit them from CLI-source selection unless explicit ownership or a new reverse-closure rule is added. A crate split is not the narrow initial CI fix.

**Next PR:** add a reviewable CLI test-root reader/owner inventory and a fail-closed checker, without changing selection. Put the checker in `scripts/` with a `scripts/test_*.py` suite and a `[[path_rule]]` in `.config/ci-test-targets.toml` assigning its own changes to `ci.yml` `script-unit`. Have it derive Cargo root identities, record the known `parity` and Phase 3 cross-target readers, shared modules, script/oracle readers, and inventory every read site that could reach test roots; unresolved directory or computed-path readers disable the exception. Run it on both sides of a candidate and expose a machine-readable closure/digest. Document the exact guarantee, fallback, and receipt requirement in `docs/ci_validation.md`. Test positive private-root/standing-reader cases and negative unknown-reader, changed-reader, helper, fixture, product source, manifest, required-package, rename, deletion, feature-change, and targeted-rebase cases. Only a later planner PR should consume a proved closure to skip CLI expansion, preserving required-target, four-shard, plan-digest, and receipt invariants. Re-evaluate the 0–24 bound on that PR's actual head before claiming a saving.
