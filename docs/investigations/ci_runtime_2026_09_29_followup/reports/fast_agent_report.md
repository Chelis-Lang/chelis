## What sets the wall time

In the September 22-29 sample, Fast ran in all 20 selected successful CI runs: median job **18.9 min**, median gate step **15.6 min**, and median job-start-to-gate-start **2.2 min**. Fifteen used hosted runners; five used warm runners. Fast plus its dependent `Integration Tests (Linux)` check finished last in 12/20; `Lint and Unit Tests (Linux)` finished last in seven, telemetry in one. On the 14 hosted runs from late September 25 onward, Fast's dependent check finished last in 11. A Fast-only gain cannot shorten a run where another required job finishes later.

The current #2754 run used a hosted runner: Fast job **22m53s**, disk cleanup **1m56s**, setup **34s**, Cargo cache restore **50s**, gate **19m16s**. Its `target/ci-fast/timing.json` separates the serial gate driver into product build **64s**, five compile/list calls **215s**, five Nextest executions **872s**, and a few seconds of receipt work. The main Nextest group alone took **818s** for 5,371 cases; the other groups added 54s for 119 cases. `gate.py` reports one outer command, while `ci_test_targets.py` supplies this useful internal breakdown. Product builds supply binaries and libraries needed by integration tests; compile/list verifies exact selected binaries before any test runs. These are real sequential prerequisites, but test execution dominates.

The longest JUnit case was the claimed-join canary at **243s**, yet its log shows it passed at 07:08:37, nearly seven minutes before the main Nextest group ended. The source-architecture unit test took **224s** and finished **last (5,371/5,371)** at 07:15:24. The gate then ran its remaining feature groups. Two other sampled hosted logs put that source test at 122s and 225s, finishing before the gate end; a September 29 log before #2754 measured 476s and finished last. These runs changed heads and workloads, so they do not isolate runner CPU contention or prove a remaining scanner algorithm defect. They do show that the test's *placement* can expose several minutes on the Fast tail. #2754's fork change is present; its 224s successful receipt does not establish a steady speedup.

## Next PR: prioritize the long source guard in the existing Nextest group

Add one exact `[[profile.ci-fast.overrides]]` rule in `.config/nextest.toml` assigning `priority = 100` to `binary_id(/^chelis-compiler-api$/) & test(/^source_arch::guarded_upper_consumers_do_not_recreate_the_semantic_pipeline$/)`. Nextest's [test-priority contract](https://nexte.st/docs/configuration/test-priorities/) runs higher-priority tests first; equal-priority tests currently sort by binary and test name, consistent with this test's late start. The #2754 hosted log installed cargo-nextest 0.9.146. This starts the workspace source guard near the beginning of `run_tests_0`, overlapping its wall time with the other 5,370 cases. Keep all Cargo selectors, test filters, product builds, five groups, JUnit uploads, and exact coverage receipt checks. The proposed change is one profile-local scheduling rule; it neither drops a required Fast assertion nor adds a hosted job.

Run the source guard itself and the existing `scripts/test_ci_test_targets.py`, `scripts/test_nextest_profile_partition.py`, and `scripts/test_ci_cadence.py` checks. In **2-3 baseline/candidate pairs** on GitHub-hosted runners, hold the base and test inventory fixed (candidate differs only by this profile rule); compare Fast job and gate wall, `build_products`, every `compile_and_list_tests_*` and `run_tests_*` timing, source-test start/pass log stamps, and the latest independent required-job finish. Require identical selected/executed binary and case identities, a successful standing coverage digest and required integration check, no timeout/new failure, and no material build/list or other-case regression. A useful go/no-go target is **at least 90s median reduction in Fast job and complete CI critical-path wall** across the pairs; reverse the priority if CPU competition erases it. The single #2754 run offers an optimistic Fast ceiling around 224s, not a promised saving. Test priority only reorders work, and overlapping CPU-heavy cases may slow one another.

At the supplied cadence of **1,857 completed CI runs in three weeks**, a measured 90s saving on every Fast-eligible run would be at most **15.5 runner-hours/week**. Applying the sample's 49/60 Fast incidence gives about **12.7 hours/week**, before docs-only and other required-job limits; at the repository's `$0.006` standard Linux minute estimate (`scripts/ci_pr_lifecycle_report.py:52`), that is roughly **$4.6/week** before per-job rounding and discounts. The main benefit would be repeated PR wait. Manual package expansion's much longer census cases occur at final-candidate dispatch and do not set this routine Fast path.

## Selection boundary

A later option is to run the source guard only for changes under its guarded source roots or to the guard itself, while retaining a trusted unchanged-base result and nightly full scan. It could remove its entire cost on some PRs, but today it is a default-feature **unit** that Fast promises to execute on every code PR. `ci_test_targets.py` explicitly rejects filtered non-ignored tests; a path-only exclusion would require a reviewed replacement owner, authenticated reuse bound to the exact candidate/base and guarded-path closure, and negative tests for omitted inputs. Current timing evidence does not justify that coverage-contract change. Keep it out of the proposed scheduling PR.
