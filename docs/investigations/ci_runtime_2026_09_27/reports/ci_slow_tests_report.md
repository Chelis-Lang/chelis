## Why they are slow, and safe changes

**Census (ranks 1–2).** These are already **outside Fast Tests and change-owned** on this candidate; manual expansion selects them, and the nightly dtype oracle independently owns them. They must keep exact candidate verification at final expansion because §C6 rejects an unclassified numeric entry. Their Python verifiers build Rustdoc JSON, examples, test binaries, executable probes, and mutation controls in nested Cargo namespaces; the JUnit itself gives no subphase timing. A recent nightly does: [hosted dispatch 36289743061](https://github.com/Chelis-Lang/chelis/actions/runs/36289743061) measured wire 1,058s and bindings 2,149s. Its `script-tests-census` timing artifact records, within the wire leg, 173s building compiler/types examples, 178s compiling the CLI test, 153s compiler-API `cargo rustc`, 90s compatibility-test compile, and 85s tide-test compile. Within bindings it records two 171/165s `chelis-python` rustc calls, 148s CLI-test compile, 105s Python payload-test compile, and 97s compiler-JSON probe build. The instrumented subprocess totals (1,042s wire, 1,330s bindings) leave binding orchestration time unclassified; these are evidence of repeated nested compilation, not a full profile.

The shared `target/agents/729-capacity-rustdoc` path in `scripts/capacity_census_typed.py` saves work **only on one runner**. Expansion assigns wire to shard 0 and bindings to shard 3, which have separate filesystems. [PR #1165](https://github.com/Chelis-Lang/chelis/pull/1165) measured a warm second leg benefit in August, when the verifiers were much smaller. That result cannot be projected onto today's 18/29-minute cases. In fact, nightly deliberately groups both on one runner, restores/saves the nested Rustdoc cache (`heavy-e2e.yml:217–260`), and [September 27's hosted dtype run](https://github.com/Chelis-Lang/chelis/actions/runs/36289743061) executed wire **then** bindings in 1,058 + 2,149 = **3,207s**, versus expansion's parallel longest case of 1,731s. [September 26's warm-runner nightly](https://github.com/Chelis-Lang/chelis/actions/runs/36215086544) took 1,028 + 1,238 = 2,266s. Co-locating expansion's two cases without a new measured speedup would likely **increase** wall time. Keep them parallel. First extend the existing nested subprocess timing artifact to manual expansion, then compare an exact-head cache-restore experiment against no restore (including cache download time, source freshness and baseline integrity). Caching compiler outputs is acceptable only when the existing current-source, execution, and mutation checks still run; neither saved JSON nor a prior pass may substitute for those checks.

**Extent matrix (ranks 3, 7, 9, 11–13, 15–16, 18).** `runtime_extent_claim_preparation.rs` calls `observe` separately for every route. `call_matrix` triples each logical fixture into export, top-level binding, and root, and `observe` invokes `chelis check`, often `chelis eval`, `chelis build`, a C compile/link, and the binary. The 120-route rank-3 test alone took 278–283s. Its target consumed 914s in #2586 change-owned shard 0, whose shard execution lasted about 22 minutes. The source provides the normative links: spec/04 §4.7 and §4.7.3, [05-MOV-1], and `spec/design/runtime_extents.md` C5. **Keep the target's current selection**: new/directly modified integration targets are required; otherwise affected-package expansion/nightly supplies breadth. It is not a standing Fast target. Add per-stage and per-route timings first. Then group cases that share one Chelis source/build into a dispatchable compiled artifact, retaining three independently asserted call routes, each expected trap/value, checker signature, Eval path, and public C entry execution. A single compiled binary can dispatch separate cases in separate processes so a trap still terminates only its own observation. Benchmark the 120-route and 69-route tests before rewriting the whole suite. Rank 18 is legitimately replaced by rank 13's explicit-key claim, so it should not be resurrected for timing's sake.

**Fast-only standing work (ranks 4–5).** Rank 4 is a standing integration on #2586: 100 cells × three lanes, with each cell checking both selected-arm values and claim failures, including reviewer-found regressions. It is about 4.3 minutes but cannot simply disappear from Fast without changing a reviewed standing contract. Reduce repeated `chelis build`/C compile by batching same-source cells and dispatching the cell index; preserve the 100-cell matrix and a separate Eval/C verdict per cell. A later split into a small standing canary plus full change-owned/expansion/nightly matrix is viable only if the canary names the red witnesses and the coverage contract explicitly permits the remaining cells to lose every-push PR execution. Rank 5 is a **unit test in `src`**, automatically selected by Fast, not a standing-integration row. It reparses all guarded Rust source with `syn`; A/C's 225–240s versus F's 65s is high variance without per-file timing, so profile file count/parse/inspection before changing the scanner. Keep the complete workspace-scope guard at PR time; moving it to nightly by deleting a row is not possible.

**Other CLI matrices (ranks 6, 8, 10, 20).** Ranks 6/10 each build and run two programs (invalid validation trap and valid later trap) for six initialisers in Eval and C; under-grad adds graph lowering. They are #2586 change-owned because that target is new, not newly added to Fast. Reuse one package setup and compile a module with named initialiser cases, then dispatch each trap path separately; retain all six, both parameter outcomes, and the host/DAG/C distinction. Rank 8 is already **manual expansion** on this candidate. It generates one large 9×9 dtype product, so its 77–156s variance calls for timing the Eval, C build/link, and run stages before narrowing the product. Rank 20 is also manual expansion; 26 combinator cases run bad and good variants through both Eval and C, causing many CLI/build invocations. Batch buildable independent cases, preserving the primitive-specific trap context and value controls. Moving either expansion test to nightly-only would remove final-head evidence without a replacement.

**C sanitizer matrices (ranks 14, 17, 19).** These are change-owned on #2586 because its C target changed; otherwise package expansion/nightly covers them. `checked_indexing_run` writes generated C and a harness, launches `clang` with ASan/UBSan, links the runtime, and executes once **for each matrix cell**. Rank 19 alone has nine payload dtypes × two index dtypes × three sparse operations. Produce fewer translation units with unique per-case entry names and compile/link once per group, then execute each case as a separate process under the same sanitizers; keep the independent bit maps, zero-size cases, and negative mutation controls. The separate required `Backend Sanitizers` job repeats C **lib units** under sanitizers, not these integration testcases, so it is not a duplicate execution of these three.

## Cadence decision and duplication

No top-20 case is among the **466 same-candidate Fast/manual duplicate identities** reported for A+B. The current long-tail problem is nested compilation and large repeated fixture matrices, rather than duplicated execution of these particular slow cases. The exact Fast/manual overlap should still be removed through authenticated evidence reuse, but that optimization will not shorten the two census critical paths. Fast runs all default-feature lib/bin units plus reviewed standing integrations; moving a long unit test such as rank 5 is a coverage-contract change, not a `.config/ci-test-targets.toml` edit. Per [`docs/ci_validation.md` §CI ownership](https://github.com/Chelis-Lang/chelis/blob/71815c2802b96767577fdc0144aab5de68535f77/docs/ci_validation.md#L269-L315) and [the PR-author guard](https://github.com/Chelis-Lang/chelis/blob/71815c2802b96767577fdc0144aab5de68535f77/docs/guard_changes_for_pr_authors.md#L172-L240), deleting, renaming, ignoring, or filtering a required identity needs an intentional reviewed replacement. I recommend **no nightly-only move today**. Most expensive non-census cases already run conditionally on a changed target or in explicit final-candidate expansion, and the two unconditional Fast cases protect distinct PR-time failures. Profile and batch their setup first; any later cadence change should state which exact PR-time assertion remains and which full matrix becomes nightly/manual.
