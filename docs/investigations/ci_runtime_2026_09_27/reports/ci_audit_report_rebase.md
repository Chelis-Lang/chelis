# Rebase reuse and cache census audit (2026-09-27)

## Rebase reuse finding

The quoted run [36318226709](https://github.com/Chelis-Lang/chelis/actions/runs/36318226709) is **PR #2586**, head `d8d7feaac8b95f0affa9a15808ec25888850e9e8`, after #2553 had merged into `main` as `71815c2802b96767577fdc0144aab5de68535f77`. The detector log says `PR_NUMBER: 2586`, `CANDIDATE LIFECYCLE: PASS: base-merge`, then `REBASE REUSE: FAIL: current synthetic candidate must have exactly two parents`. The synthetic candidate `9716a2581bed93cc958b1abba47bf4a388889de5` actually has two parents on GitHub: `71815c2` and `d8d7fea` (`gh api repos/Chelis-Lang/chelis/git/commits/9716a258...`). The message is therefore false for the commit itself.

The cause is a shallow clone mismatch. `ci.yml` checks out the exact candidate with `fetch-depth: 1`. `scripts/ci_establish_candidate_clone.py` lines 202-239 establishes the base/head objects and pairwise merge bases, but its invariant does not require Git's traversal to see the candidate's parent edges. The job reported `CANDIDATE CLONE: PASS` and kept the candidate as a shallow graft. `scripts/ci_rebase_reuse.py` lines 228-238 reads parents using `git show -s --format=%P`, which respects the shallow graft and returns no parents. In contrast, `scripts/ci_candidate_identity.py` lines 65-100 already reads the raw `git cat-file commit` header and explicitly explains why it does so for shallow boundaries. The identity step succeeded on the same candidate. The reuse verifier fails closed, and `ci.yml` lines 389-410 selects the full lane.

This is a real verifier bug. An especially clear lost opportunity is [PR #2499 run 36040612155](https://github.com/Chelis-Lang/chelis/actions/runs/36040612155): it classified a base merge and hit the same parent error. Its preceding head `fbb4cfd7a25c8f4080e346ea790a942d3a76bfba` had a successful trusted [candidate receipt run 36036904548](https://github.com/Chelis-Lang/chelis/actions/runs/36036904548), artifact `10825397505`; the receipt has `reuse_eligible: true`, empty blockers, and passing required checks. That proves the parent error prevented the verifier from considering eligible prior evidence, though later frontier checks could still have selected full CI. For #2586, artifact lookup for event `before=492dece170a84cc935d20ccd48be21280887247a` found **zero** prior candidate receipts, so fixing the parent bug alone would likely still select full CI for that run. The verifier does not print receipt availability before this error, so its final lane after repair is not directly observed.

For a systematic sample, I listed 205 recent PR CI runs dated September 23-27, sampled every fifth run (40), and read detector logs. One sampled run was still in progress. Of the 39 others, 29 logged this exact false parent failure, two logged `FULL: prior trusted receipt unavailable`, seven were initial candidates with no reuse attempt, and one cancelled run had no decision. None logged a targeted or docs reuse lane in this sample. The parent failure also appears on ordinary review-repair pushes; those would run ordinary full CI anyway, so the runtime consequence matters most for base merges and rebases. Among five sampled base updates, three hit the false parent failure and two correctly selected full for missing receipts. This is a sample, not a census of all 205 runs.

**Recommended repair:** make `ci_rebase_reuse._candidate_parents` read validated parents from the raw commit object, using the same helper/logic as `ci_candidate_identity._commit_parents`. Add a regression fixture whose synthetic candidate remains a shallow graft after clone establishment, with a trusted eligible prior receipt; assert the verifier reaches the correct targeted/docs/full policy decision rather than failing parent validation. Keep its head-parent check and remaining receipt/frontier safety checks. Strengthening the clone invariant to force an unshallow fetch would also fix the symptom but would sacrifice its deliberately cheap common path.

## Issue #2673

[Issue #2673](https://github.com/Chelis-Lang/chelis/issues/2673) describes a real opaque failure. `scripts/capacity_census_cache_publication.py` line 162 emits only `wrong compile outcome: library` when the expected-success fixture fails, although `CompileOutcome` already holds rustc stderr and line 416 writes `<case>.stderr`. The fixture includes `cache_envelope.rs` via `#[path]` and line 344 fixes the `--extern` crate set. Printing a bounded compiler diagnostic plus the saved stderr path, and documenting this fixture constraint beside the source, are direct fixes. Turning `cache_envelope` into a standalone crate is materially larger: the file currently seals `CachePayload` to `crate::LibraryContext` and `crate::StdLibContext` (source lines 60-91), so extraction requires redesigning that owner boundary, not merely adding a `Cargo.toml`.
