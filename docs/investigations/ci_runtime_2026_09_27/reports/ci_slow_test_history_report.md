**Bounded audit, 2026-09-27.** The companion [rank, introduction, purpose, and optimization report](ci_slow_tests_report.md) defines the original 20 identities and six-run timing sample. I queried CI run history for 16 introducing or major follow-up PR branches: **83 CI runs, 27 failed overall** (August 1–September 27). I inspected failed job names and 10 representative failed-run logs, searched issue/PR references to exact identities and test binaries, and parsed all five full-workspace/dtype JUnit artifacts from [September 16 Linux Extended Validation run 35052203536](https://github.com/Chelis-Lang/chelis/actions/runs/35052203536). This is a directed audit, **not all PRs since each introduction**; an unobserved failure below is not proof that a test never failed. Successful shard jobs can contain failed informational receipts, and older per-run artifacts are unevenly available. Count a unique cause, not every red test or derivative aggregate job.

**New entrant since the companion sample:** [#2612](https://github.com/Chelis-Lang/chelis/pull/2612) introduced `chelis-cli::issue_2567_deep_eval_values::a_deep_chain_through_dict_values_returns_as_a_root`; [manual expansion run 36327831748](https://github.com/Chelis-Lang/chelis/actions/runs/36327831748) measured 99.7 seconds, placing it around current rank 17 and pushing sparse sanitizer below the current top 20. #2612's three CI runs had two green and one failed; the failed run's reported jobs do not establish this testcase as the cause. The test protects a real deep-chain stack-overflow fix; the implementation still copies the accumulator quadratically, tracked in #2592. Profile depth/copy phases before reducing the stress depth or moving it to nightly.

**One failure class, eight rows:** In [Sept 16 nightly JUnit](https://github.com/Chelis-Lang/chelis/actions/runs/35052203536), ranks **3, 7, 9, 11, 12, 15, 16, 18** failed with the same `unknown exported fixture ABI` assertion after #2105 changed C symbol spelling. [The #1783 audit](https://github.com/Chelis-Lang/chelis/issues/1783) bisected the broader class and says #2113 repaired the `runtime_extent_claim_preparation` binary. This is evidence that the long matrix noticed integration breakage after merge, **not eight independent semantic catches**. #1917 and #1788 add distinct semantic failures, but they too were found outside a successful required PR gate. The targeted selection policy should be checked against C ABI/exporter and runtime-claim owners before reducing cadence.

**Recommendation:** No blanket nightly move follows from this sample. The two most expensive censuses already avoid every-push Fast and run at exact-head manual expansion/nightly; moving them farther would remove the final numeric-authority check. Most long CLI/C matrices are conditional change-owned or manual expansion. The sole large unconditional new Fast case is #2586's claimed-join matrix, whose history is too short to infer a low failure yield. Run the batching/profiling experiments in the companion report, then compare per-test cost and distinct before-merge catches over a complete 30–60-day CI/expansion receipt census. In that census, classify PR gate, manually dispatched final-head expansion, local pre-push, and post-merge nightly separately; use test-level JUnit and candidate-versus-base receipts rather than overall red run counts.
