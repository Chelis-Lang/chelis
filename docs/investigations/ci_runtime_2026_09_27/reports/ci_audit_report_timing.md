# CI timing audit, 2026-09-23 through 2026-09-27

Read-only GitHub Actions sample. Workflow wall time is `updated_at - created_at`; job queue time is `started_at - created_at`; job execution is `completed_at - started_at`. September 27 was still in progress when queried, so the figures below exclude unfinished runs. These are elapsed times, not billed minutes.

## Distribution and runner transition

For successful `pull_request` CI runs, daily median wall times were 13.9 min (29 runs, Sep 23), 14.9 (38, Sep 24), 22.9 (29, Sep 25), 22.0 (25, Sep 26), and 22.8 (15 completed, Sep 27). Different PRs select different targets, so this is a trend, not a controlled same-workload benchmark. The September 25 distribution has large queue outliers: [run 36097607320](https://github.com/Chelis-Lang/chelis/actions/runs/36097607320) lasted 92.9 min, with **81.1 min waiting** for `chelis-ci-warm` and 10.2 min executing Fast Tests; [run 36090951831](https://github.com/Chelis-Lang/chelis/actions/runs/36090951831) lasted 84.3 min, with 67.5 min warm-runner wait and 15.1 min Fast Tests; [run 36090687635](https://github.com/Chelis-Lang/chelis/actions/runs/36090687635) lasted 51.0 min, with 39.2 min wait and 10.2 min Fast Tests.

After Fast Tests moved to `ubuntu-latest`, job execution is slower but queueing is nearly absent. On Sep 23 [run 35924329872](https://github.com/Chelis-Lang/chelis/actions/runs/35924329872), Fast Tests took 9.5 min on `chelis-ci-warm-2`, including an 8.5 min gate. On Sep 27 [run 36318226709](https://github.com/Chelis-Lang/chelis/actions/runs/36318226709), exact candidate `d8d7feaac8b95f0affa9a15808ec25888850e9e8`, Fast Tests took 22.9 min on `ubuntu-latest`, including a 21.2 min gate, with effectively zero queue. The [ci-fast receipts](https://github.com/Chelis-Lang/chelis/actions/runs/36318226709/artifacts/10931424640) show 73 sec build products, 167 sec initial compile/list, and 1,006 sec for shard 0 test execution; the older run's [receipts](https://github.com/Chelis-Lang/chelis/actions/runs/35924329872/artifacts/10778449218) show 88 sec build products, 106 sec initial compile/list, and 296 sec shard 0 execution. The test telemetry counts grew only from 5,245 to 5,375 (+2.5%); the test execution increase therefore cannot be explained by test count alone. A stable named test, `source_arch::guarded_upper_consumers_do_not_recreate_the_semantic_pipeline`, measured 96 sec then 225 sec, though its implementation or inputs may also have changed. The hosted runner is materially slower for this gate, while avoiding severe warm-runner waits; the evidence does not show a GitHub-hosted queue incident.

## #2586 critical paths

[CI run 36318226709](https://github.com/Chelis-Lang/chelis/actions/runs/36318226709) lasted 28.2 min. `Detect docs-only changes` used 1.2 min and `Plan Changed Integration Tests` 0.8 min; the four change-owned buckets started at 12:14:43 UTC. The critical bucket 0 ran 25.5 min, including 2.3 min disk cleanup, 0.5 min cache restore, and **22.3 min executing the shard**. `Fast Tests` ran concurrently for 22.9 min. The report/final gate added about 0.5 min after the slow bucket. Job queue times were 0–0.1 min except minor 0.6 min isolated waits. [Bucket 0 receipt](https://github.com/Chelis-Lang/chelis/actions/runs/36318226709/artifacts/10932530376) assigns 914.3 sec of its shard to `chelis-cli::runtime_extent_claim_preparation` execution. Its JUnit's longest individual tests were `omitted_extent_claim_contract` 278.4 sec, `computed_claim_result_graph_contract` 163.5 sec, and `staged_reshape_sources_preserve_captures_and_order` 154.9 sec. JUnit test times overlap under parallel nextest execution; do not sum them as wall time. Bucket 1's longest individual tests were `chelis-backend-c::exec_compile` sanitizer cases at 121.4, 98.7, and 82.3 sec.

The matching [manual package expansion 36318230980](https://github.com/Chelis-Lang/chelis/actions/runs/36318230980) lasted 49.8 min. Its run SHA is `main`, but its [summary artifact](https://github.com/Chelis-Lang/chelis/actions/runs/36318230980/artifacts/10932148790) verifies exact candidate `d8d7feaac8b95f0affa9a15808ec25888850e9e8` and base `71815c2802b96767577fdc0144aab5de68535f77`: 599 covered targets, zero introduced, inherited, or unrun. Plan was 0.8 min, then four parallel buckets took 48.1, 40.0, 22.8, and 17.0 min; summary took 0.6 min. Bucket 3 spent 46.3 of 48.1 min in its execution step, not setup or queue. Its [JUnit/receipt artifact](https://github.com/Chelis-Lang/chelis/actions/runs/36318230980/artifacts/10932442605) records `chelis-python::capacity_census_bindings::registered_pyfunctions_match_the_reviewed_rustdoc_signatures` at **1,699.7 sec (28.3 min)**. Bucket 0's `chelis-compiler-api::capacity_census_wire::wire_schema_numeric_fields_match_the_reviewed_baseline` took 1,101.8 sec (18.4 min). A second #2586 [expansion 36321480379](https://github.com/Chelis-Lang/chelis/actions/runs/36321480379), candidate `4a893d078e2df1e7a86cc9551a03ec06fcd97feb`, lasted 52.4 min; the same binding census test took 1,731.4 sec. These are repeatable long tests, not a one-run queue anomaly. A Sep 24 [expansion 35968945718](https://github.com/Chelis-Lang/chelis/actions/runs/35968945718) lasted 38.8 min; it selected a different set (561 targets), including a 974.7 sec wire census test, so it is not a direct same-test comparison for the binding census.

The binding test calls `run_typed_enumerator` in `crates/chelis-python/tests/capacity_census_bindings.rs`. That launches `scripts/capacity_census_typed.py bindings-discovery` through `tests/support/capacity_census_compiler_json.rs`. The Python path runs nested Cargo rustdoc, a compiler-JSON probe build/execution, and native verification in `target/agents/729-capacity-rustdoc`; its source comments explain why it uses a separate target. The expansion bucket 3 log says `No cache found` at its Cargo restore step. **Inference:** much of the 28-minute JUnit time is nested build/verification work on the hosted runner. The available JUnit records only total test time; it does not split the nested commands, so a more precise attribution would need their process-timing receipts. The expansion's setup steps total roughly 2 min and do not explain 50 min wall time.

Sampling limits: I inspected jobs/steps for selected runs and JUnit/receipt artifacts for the cited runs, rather than every job in all 265 CI and 80 expansion runs. The 2026-09-27 #2586 run 36327834681 was still active when sampled; elapsed-so-far and absent jobs from that run cannot be interpreted as successful reuse or final runtime.
