## Context

`chelis-reef` combines deterministic manifest, lockfile, graph, linking, pin, origin, and reconciliation logic with blocking network fetches, environment and credential discovery, filesystem mutation, subprocesses, locks, and notices. `chelis-conformance` similarly performs policy checks and reconciliation while directly walking and mutating a live repository.

These workflows are not generally one-shot planners: observed metadata or downloaded manifests can reveal additional dependencies and decisions. They therefore use a resumable domain protocol before a final closed transaction plan. This change follows `.openspec/FCIS_ARCHITECTURE.md` and is independent from lint snapshots.

## Goals / Non-Goals

**Goals:**

- Make every value capable of changing Reef or conformance policy an explicit initial input or validated observation.
- Keep version, origin, pin, dependency, repair, and follow-up-request decisions in the functional core.
- Give large package/generated bytes content-addressed ownership across observation and mutation.
- Produce and validate a closed plan before acquiring a mutation lock or changing state.
- Revalidate prerequisites after lock acquisition and before the first mutation.
- Preserve package security, transaction atomicity, idempotency, formats, and fail-closed behavior.
- Return notices and reports as data.

**Non-Goals:**

- Replacing package format, registry protocol, or lockfile schema.
- Pretending network-dependent resolution is knowable as one upfront static plan.
- Making install, publish, or reconciliation execution side-effect free.
- Serializing secret bytes, OS handles, or ephemeral staging paths into plans or replay records.
- Sharing a generic workflow framework with compiler, evaluator, proof, or lint code.

## Decisions

### 1. Exact core and adapter boundaries

A new dependency-minimal `crates/chelis-reef-core` crate owns manifest/lock parsing, dependency and origin selection, pin policy, package validation over supplied bytes, workflow state, replay, query identity, and final plan construction. It has no `reqwest`, process, filesystem, credential, terminal, or locking dependency.

`crates/chelis-reef` becomes the adapter/executor crate for snapshot collection, registry/network transport, blob storage, credentials, subprocesses, locks, mutation, and rendering integration. In `chelis-conformance`, planned `model.rs`, `analysis.rs`, and `planning.rs` are designated decision modules over supplied snapshots; existing/live collection and scaffold mutation move under adapter modules. CLI and `reef setup` remain outer shells.

A checked-in manifest records the exact transitive production set. Architecture fixtures reject direct, aliased, re-exported, qualified, callback-hidden, and trait-hidden host capabilities and classify `cfg(test)` bodies without exempting production code.

### 2. Host-dependent decisions are resumable

The workflow core advances from immutable local/package snapshots, command options, repository metadata, resolved non-secret host configuration, available capabilities, and prior observations to one of:

- accepted read-only analysis;
- semantic rejection diagnostics;
- one correlated request plus non-cloneable continuation;
- a final validated-plan candidate;
- protocol failure.

Requests cover decision-bearing filesystem observations absent from snapshots, registry metadata, package blobs, opaque credential lookup references, subprocess output, and lock-state observations. Deterministic invocation-local request identities start at zero. Responses are correlated, typed, integrity-checked, size-bounded, single-use, and normalized for replay. The core, not an adapter, decides the next request.

### 3. Host facts and secrets are separate

Outer adapters resolve home/cache roots, platform, endpoints, drift policy, external binary descriptors, limits, capabilities, and opaque credential identifiers. Secret bytes are provided only to the authorized executor at use time. They never enter workflow state intended for persistence, blobs, plans, query keys, observations, notices, diagnostics, or replay records.

Missing credentials or capabilities fail explicitly. The workflow does not consult environment variables or invoke `gh` as a fallback.

### 4. Decision-bearing bytes use content-addressed ownership

A package-byte or generated-content observation either contains bounded in-memory bytes or a `VerifiedBlobRef { digest, size, media_type }` issued by an explicit `BlobStore` adapter. Persistent workflow records and final plans use only verified blob references. Ephemeral paths and process-local handles are forbidden.

Before planning, the core validates manifest, archive, origin, digest, signature evidence, and declared size over the supplied bytes/reference metadata. Before staging, the executor reopens the blob through the authorized store, verifies size and digest again, and fails closed on absence or drift. Blob lifetime extends through transaction completion; cleanup is an executor report obligation. This permits large artifacts without embedding them in every plan while preventing ambient-file substitution.

### 5. Discovery completes before final planning

A final `MutationPlan` is produced only after all observations capable of changing dependency, origin, verification, path, content, or transaction decisions are available. Reads and downloads with decision-bearing results are workflow requests, not blind plan actions.

The plan contains traversal-safe relative destinations, verified blob references or bounded inline bytes, links/removals, expected prior-state fingerprints, and transaction obligations. It cannot contain unresolved discovery, secret material, ambient absolute source paths, or unknown action kinds.

### 6. Plan validation and transaction execution are distinct

Pure whole-plan validation checks every action, relative path, digest, blob reference, transition, containment rule, precondition, and transaction invariant before any executor event. A malformed final action therefore causes zero lock or mutation events.

For real execution the transaction protocol is:

```text
validate plan -> acquire mutation lock -> revalidate prerequisites and blobs
-> stage -> verify staged state -> atomic commit -> cleanup/report
```

A drift or blob failure after lock acquisition performs no state-changing mutation. Failure after staging invokes rollback/cleanup semantics and preserves prior committed state. Lock acquisition, revalidation, rollback, and cleanup are transaction events/obligations, not ordinary unconditional file mutations. Execution never proceeds unlocked.

Dry run performs the same authorized discovery and pure plan validation, renders that final plan, and performs no mutation-lock or transaction-execution event. It does not claim that a later execution will succeed without prerequisite revalidation.

### 7. Executors are capability adapters, not policy engines

Filesystem, blob, network, process, credential, lock, and mutation adapters execute typed requests or transaction states and return observations/reports. They do not select versions, origins, pins, dependencies, managed-block policy, or repairs. Rendering is separate from execution.

The mutation executor preserves checksum/signature verification, archive validation, path containment, same-filesystem atomic rename, advisory locking, no-silent-fallback behavior, and deterministic recovery reporting.

### 8. Conformance is part of the boundary

`chelis-conformance` audit checks consume a collected `ConformanceSnapshot`; managed-block, pin, narrowing, skill, workflow, and registry decisions do not read the live repository. Init, sync, and bump produce the same workflow/final-plan types or delegate pure plan fragments to Reef orchestration. Legacy direct-I/O functions may remain only as temporary path adapters that collect/execute and are not counted as core evidence.

This prevents migrating `chelis reef conform` call sites while leaving policy-bearing scans inside `chelis-conformance::audit`.

### 9. Identity and replay are explicit

`ReefQueryKey` covers immutable initial snapshots, command options, policy versions, non-secret resolved host configuration, capability declarations, registry identities, and relevant limits. It excludes observations and is usable before host execution.

`ReefPlanDigest` covers the query key plus normalized observations, verified blob digests, diagnostics, and final plan. `ExecutionReport` adds lock timing, adapter logs, staging locations, cleanup detail, and renderer metadata; those fields do not alter the query key or plan digest.

Replay starts a fresh workflow from equal initial inputs and feeds the normalized observation transcript. It performs no host action and cannot reuse a consumed continuation.

### 10. Compatibility and idempotency remain executable

Established install, fetch, publish, source-sync, wiring, conform, audit, and doctor fixtures compare exit status, machine shape, notices, dependency/pin/origin decisions, and final on-disk state. Malicious, corrupt, conflicting, incomplete, denied, and drifted inputs retain fail-closed outcomes.

Conform sync and setup reconciliation produce no state-changing actions once desired state is reached. Single-artifact drift produces only the necessary repair.

## Risks / Trade-offs

- **Workflow complexity:** migrate one command family at a time over a small closed vocabulary.
- **Large blobs:** content-addressed ownership avoids plan copies but requires explicit lifetime, digest revalidation, and cleanup tests.
- **Host drift:** lock then revalidate prerequisites/blobs before mutation.
- **Transaction regressions:** capture traces and inject failure at each lock/revalidate/stage/verify/commit/cleanup boundary.
- **Conformance scope:** include its decision modules explicitly rather than claiming call-site-only FCIS.
- **Public compatibility:** retain path adapters during migration, but do not count them as pure-core completion while they contain policy-bearing I/O.

## Migration Plan

1. Capture current command, request, mutation, notice, and failure traces; add protocol, blob, plan, transaction, denial, replay, and conformance-snapshot test stubs.
2. Create `chelis-reef-core`, resolved configuration, domain requests/observations, deterministic identities, query keys, plan digests, and blob-reference types.
3. Migrate read-only Reef audit/doctor and conformance audit to snapshot/workflow analysis.
4. Add whole-plan validation and transaction executors with lock-then-revalidate behavior.
5. Migrate fetch/install, publish, source sync/wiring, and conform init/sync/bump one command family at a time.
6. Remove policy-bearing direct host access after each family passes its focused parity gate.
7. Run the umbrella acceptance oracle only after every designated family is migrated.

Rollback is command-family scoped and preserves on-disk formats. It must not restore silent credential fallback, ambient blob substitution, unlocked mutation, or an FCIS completion claim for direct-I/O policy code.

## Acceptance Oracle

The authoritative completion oracle is:

```text
.venv/bin/python scripts/fcis_gate.py reef-workflows
```

The runner must execute request/observation correlation and replay, query-key/plan-digest identity, blob ownership and revalidation, full-plan validation, lock-then-prerequisite revalidation, dry-run, capability denial, transaction failure injection, package security, idempotency, Reef CLI parity, conformance snapshot/planning parity, and structured notice/report fixtures against one revision. Success means exit status 0, an empty reported error list, no host action in denied/replay fixtures, no mutation-lock or mutation event in dry run, and no successful partial state after any injected transaction failure.

## Deferred Follow-ups

- Plan serialization remains out of scope until redaction, stable schema, and blob-lifetime guarantees pass the acceptance oracle.
- Notice codes remain internal structured fields unless a separate machine-API compatibility proposal promotes them.
