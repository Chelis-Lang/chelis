## Context

`chelis-reef` combines deterministic manifest, lockfile, graph, linking, pin, origin, and reconciliation logic with blocking network fetches, environment and credential discovery, filesystem mutation, subprocesses, locks, and notices. `chelis-conformance` similarly performs policy checks and reconciliation while directly walking and mutating a live repository.

These workflows are not generally one-shot planners: observed metadata or downloaded manifests can reveal additional dependencies and decisions. They therefore use a resumable domain protocol before a final closed transaction plan. This change follows `.openspec/FCIS_ARCHITECTURE.md` and is independent from lint snapshots.

## Goals / Non-Goals

**Goals:**

- Make every value capable of changing Reef or conformance policy an explicit initial input or validated observation.
- Keep version, origin, pin, dependency, repair, and follow-up-request decisions in the functional core.
- Give large package/generated bytes content-addressed ownership across observation and mutation without trusting adapter-issued metadata as inspected package content.
- Produce and validate a closed local mutation plan before acquiring a mutation lock or changing state, and use a separate idempotent plan for irreversible remote actions.
- Acquire every required lock in canonical order and revalidate prerequisites after lock acquisition and before the first mutation.
- Preserve package security, explicitly scoped atomicity, idempotency, formats, and fail-closed behavior without claiming global atomicity across unrelated paths or remote systems.
- Return notices and reports as data.

**Non-Goals:**

- Replacing package format, registry protocol, or lockfile schema.
- Pretending network-dependent resolution is knowable as one upfront static plan.
- Making install, publish, or reconciliation execution side-effect free.
- Claiming that remote publication or a multi-root conformance repair can be rolled back atomically like one same-filesystem package-root rename.
- Serializing secret bytes, OS handles, or ephemeral staging paths into plans or replay records.
- Sharing a generic workflow framework with compiler, evaluator, proof, or lint code.

## Decisions

### 1. Exact core and adapter boundaries

A new dependency-minimal `crates/chelis-reef-core` crate owns manifest/lock parsing, dependency and origin selection, pin policy, package validation over supplied bytes, workflow state, replay, query identity, and final plan construction. It has no `reqwest`, process, filesystem, credential, terminal, or locking dependency.

`crates/chelis-reef` becomes the adapter/executor crate for snapshot collection, registry/network transport, blob storage, credentials, subprocesses, locks, mutation, and rendering integration. In `chelis-conformance`, planned `model.rs`, `analysis.rs`, and `planning.rs` are designated decision modules over supplied snapshots; existing/live collection and scaffold mutation move under adapter modules. CLI and `reef setup` remain outer shells.

Cargo dependency allowlists on `chelis-reef-core` are the primary architecture boundary. A checked-in manifest records the designated conformance decision modules that temporarily remain in the mixed crate. Through contract mechanics, the accepted `establish-dylint-tooling` prerequisite's pinned `chelis-fcis-boundaries` library consumes those core/adapter/module boundaries and the declared Reef-core and conformance package/library/test/feature lanes from the FCIS manifest. It rejects resolved direct, alias, re-export, qualified, function-item, callback, trait, declarative-macro-expanded, and adapter-module references to filesystem, network, process, environment, credentials, locks, clock, terminal, entropy, scheduling, unsafe-FFI, or mutable-global capabilities, plus public callback/function-pointer/unsealed-trait or capability-handle inputs. Unresolved configured entries, zero matched production-core/decision-module items, or omitted declared lanes fail closed.

Allowed-positive and violating-negative Dylint UI detector fixtures classify production functions compiled in test lanes separately from true `cfg(test)` owners and prove each claimed syntax form before use. Each domain registration is `NoFix`; it may reference a machine-applicable fix only after a separately accepted Dylint-tooling change supports that fix ID and `FCIS-EVIDENCE-011` validates disposable exact-rewrite/no-machine-fix, compile/lint, Reef/conformance-plan-and-failure parity, idempotence, and checkout-immutability plans. The gate records exact pins, lanes, resolved entries, matched production counts, detector/fix states, and blind spots and does not claim coverage of unexecuted cfg/target/feature code, procedural-macro/build-script implementation effects, arbitrary dynamic dispatch, precompiled dependency behavior, or future Rust syntax.

### 2. Host-dependent decisions are resumable

The workflow core advances from immutable local/package snapshots, command options, repository metadata, resolved non-secret host configuration, available capabilities, and prior observations to one of:

- accepted read-only analysis;
- semantic rejection diagnostics;
- one correlated request plus non-cloneable continuation;
- a final validated-plan candidate;
- protocol failure; or
- host failure that cannot be interpreted as a typed domain observation.

Expected not-found, denied-capability, unavailable-registry, child-exit, timeout, and lock-state outcomes are typed observations when policy must interpret them. Malformed correlation, response kind, bounds, or integrity is protocol failure. Adapter breakage that cannot be represented by the closed observation vocabulary is host failure. Partial local execution and indeterminate remote acceptance belong to execution-report algebras, not semantic rejection.

Requests cover decision-bearing filesystem observations absent from snapshots, registry metadata, package blobs, opaque credential lookup references, subprocess output, and lock-state observations. Deterministic invocation-local request identities start at zero. Responses are correlated, typed, integrity-checked, size-bounded, single-use, and normalized for replay. The core, not an adapter, decides the next request.

### 3. Host facts and secrets are separate

Outer adapters resolve home/cache roots, platform, endpoints, drift policy, external binary descriptors, limits, capabilities, and opaque credential identifiers. Secret bytes are provided only to the authorized executor at use time. They never enter workflow state intended for persistence, blobs, plans, remote body digests/idempotency keys, observations, notices, diagnostics, or replay records.

The independent `require-explicit-reef-credentials` change establishes that missing credentials or capabilities fail explicitly without environment/helper discovery or `gh` fallback. This workflow accepts only its resolved opaque credential references and preserves that prerequisite contract.

### 4. Decision-bearing bytes use content-addressed ownership without adapter self-verification

A download or generated-content adapter first returns bounded inline bytes or an untrusted `BlobCandidateRef { claimed_digest, claimed_size, media_type }` retained by an explicit `BlobStore`. Adapter issuance does not make that reference verified. Ephemeral paths and process-local handles are forbidden from workflow state and persistent records.

The core exposes a pure `inspect_blob_bytes(candidate, bytes)` operation. The shell borrows immutable bytes from the retained blob without copying them into the final plan and calls that core operation. It verifies actual size/digest, archive structure, manifest, origin, signature evidence, and package policy, then returns an opaque core-constructed `InspectedBlob` containing a `VerifiedBlobRef` plus canonical inspected facts. Workflow decisions accept `InspectedBlob`, never bare adapter metadata. For artifacts above the bounded direct-inspection size, the same operation consumes deterministic ordered chunks and produces the same result; chunk boundaries are not semantic input.

Persistent workflow records and final plans use only core-issued verified references and canonical inspected facts. Before staging, the executor reopens the blob through the authorized store, verifies size and digest again, and fails closed on absence or drift. Blob lifetime extends through transaction completion; cleanup is an executor report obligation. Replay may reuse canonical non-secret inspected facts only when their digest and current verification/freshness policy validate; execution still reopens and verifies bytes.

### 5. Discovery completes before final planning

A final `LocalMutationPlan` or `RemoteActionPlan` is produced only after all observations capable of changing dependency, origin, verification, path, content, or execution decisions are available. Reads and downloads with decision-bearing results are workflow requests, not blind plan actions.

A local plan contains normalized traversal-safe UTF-8 relative destinations using `/`, verified blob references or bounded inline bytes, links/removals, expected prior-state fingerprints, lock scopes, and transaction obligations. Non-UTF-8 or `.`/`..` destination components fail before planning. It cannot contain unresolved discovery, secret material, ambient absolute source paths, or unknown action kinds.

A remote plan body contains canonical remote identities, expected remote preconditions, content digests, and ordered irreversible operations. `RemotePlanBodyDigest` is SHA-256 over the body only, excluding the idempotency key and all execution/report metadata, using the `chelis-fcis/reef-remote-body/v1\0` domain plus tagged length-prefixed canonical fields. The idempotency key is derived from that body digest under the separate `chelis-fcis/reef-idempotency/v1\0` domain and is stored in the execution envelope, eliminating any digest/key cycle. The remote plan cannot claim rollback of an operation the remote service has accepted. An uncertain transport result becomes `IndeterminateRemoteState` and requires read-only reconciliation before retry.

### 6. Local plan validation, lock ordering, and transaction execution are distinct

Pure whole-plan validation checks every action, relative path, digest, blob reference, transition, containment rule, precondition, lock scope, and transaction invariant before any executor event. A malformed final action therefore causes zero lock or mutation events.

A plan declares a `LockSet`. Executors sort and acquire the complete set by `(scope_rank, logical_identity)`, with scope ranks `toolchain_home < reef_store < project_root < conformance_root`; they never acquire a lower-ranked lock while holding a higher-ranked one. If the complete set cannot be acquired under policy, acquired locks are released before wait/retry/failure. Network discovery and credential use occur before lock acquisition.

For real local execution the protocol is:

```text
validate plan -> acquire ordered lock set -> revalidate prerequisites and blobs
-> stage -> verify staged state -> commit by declared atomicity unit
-> cleanup/recovery report
```

A drift or blob failure after lock acquisition performs no state-changing mutation. A package/store entry committed by same-filesystem directory rename is atomic for that entry. An individual managed file uses atomic replacement. A plan spanning multiple independent destinations uses a durable journal and deterministic forward/compensating recovery; it is recoverable but is not described as globally atomic. Failure before the first commit preserves prior committed state. Failure after one atomicity unit commits returns structured partial/recovery state and can never report complete success.

Lock acquisition, revalidation, rollback/compensation, and cleanup are transaction events/obligations, not ordinary unconditional file mutations. Execution never proceeds unlocked. Dry run performs the same authorized discovery and pure plan validation, renders that final plan, and performs no mutation-lock or transaction-execution event. It does not claim that a later execution will succeed without prerequisite revalidation.

### 7. Executors are capability adapters, not policy engines

Filesystem, blob, network, process, credential, lock, local-mutation, and remote-action adapters execute typed requests or plan states and return observations/reports. They do not select versions, origins, pins, dependencies, managed-block policy, repairs, remote retry policy, or whether an indeterminate publication counts as success. Rendering is separate from execution.

The local mutation executor preserves checksum/signature verification, archive validation, path containment, declared atomicity units, ordered advisory locking, no-silent-fallback behavior, and deterministic recovery reporting. The remote executor sends the plan's deterministic idempotency key, validates expected remote preconditions, and reports accepted, rejected, or indeterminate state; it never fabricates local-style rollback.

### 8. Conformance is part of the boundary

`chelis-conformance` audit checks consume a collected `ConformanceSnapshot`; managed-block, pin, narrowing, skill, workflow, and registry decisions do not read the live repository. Init, sync, and bump produce the same workflow/final-plan types or delegate pure plan fragments to Reef orchestration. Legacy direct-I/O functions may remain only as temporary path adapters that collect/execute and are not counted as core evidence.

This prevents migrating `chelis reef conform` call sites while leaving policy-bearing scans inside `chelis-conformance::audit`.

### 9. Replay, remote idempotency, and persistence scope are explicit

A fresh workflow may consume an explicitly supplied normalized, non-secret observation sequence and core-issued inspected facts for deterministic tests and audit. Replay validates correlation, integrity, policy, and inspected content through the same decision path, performs no host action, and cannot reuse a consumed continuation. Secret-bearing data and ephemeral paths are never replay inputs.

This change introduces no `ReefQueryKey`, general `ReefPlanDigest`, persistent workflow-result cache, or local-plan reuse authorization. Mutable local prerequisites and blobs are always revalidated under the ordered lock set before mutation. Remote publication alone ships a stable `RemotePlanBodyDigest` and derived idempotency key because the external API requires retry identity. `ExecutionReport` adds lock timing, adapter logs, staging locations, cleanup detail, partial or indeterminate state, and renderer metadata; those fields do not alter the remote body digest.

### 10. Compatibility and idempotency remain executable

Established install, fetch, publish, source-sync, wiring, conform, audit, and doctor fixtures compare exit status, machine shape, notices, dependency/pin/origin decisions, remote-state classifications, and final on-disk state. Malicious, corrupt, conflicting, incomplete, denied, drifted, and indeterminate inputs retain fail-closed outcomes. The approved credential correction removes implicit `gh auth token` fallback: only resolved explicit credential references may authorize authenticated requests.

Conform sync and setup reconciliation produce no state-changing actions once desired state is reached. Single-artifact drift produces only the necessary repair.

### 11. Plan authority and transaction order are type-enforced

Blob and plan authority advance through distinct private-construction types: `BlobCandidateRef` is untrusted, only core inspection can produce `InspectedBlob`, and only retained/reverified content can produce the execution capability associated with `VerifiedBlobRef`. Adapter-claimed digest or media type never upgrades the type. Sensitive credential values have no serialization/debug path into these types.

Local execution uses typestate or equivalent private constructors for `PlanCandidate -> ValidatedPlan -> LockedPlan -> RevalidatedPlan -> StagedPlan -> ExecutionReport`. An executor API cannot stage before whole-plan validation, mutate before complete ordered lock acquisition and revalidation, or construct complete success from partial/recovery state. Remote plans and reports use a separate closed state algebra, so indeterminate remote acceptance cannot inhabit local rollback or complete-success variants.

One typed registry owns request/observation kinds, local action kinds, lock ranks, transaction states, remote states, and report states. Conformance and Reef projections, docs, traces, renderers, and acceptance matrices are generated or tripwire-checked consumers.

The FCIS manifest pins exact v1 path/component, request, observation, metadata, inline-byte, chunk, direct-inspection, archive, plan-action, lock-set, transcript, journal, and total-workflow bounds. It also owns the exact result projection from expected host observations, policy denial, semantic rejection, malformed protocol, adapter failure, partial local state, and indeterminate remote state. Implementation of the protocol slice is blocked while any bound or projection is absent.

### 12. The umbrella has one explicit cross-slice invariant

The command families share one security-critical invariant that requires end-to-end completion: every policy-bearing Reef and conformance decision in the designated boundary must consume supplied snapshots/observations and produce the same closed request, plan, lock, blob-authority, and report vocabularies, with no normal command path retaining a direct-I/O policy bypass. Removing compatibility paths safely therefore requires the read-only, local transaction, conformance, source-wiring, and remote-publication slices to agree on those types and evidence.

Each command-family slice remains independently reviewable, has its own registered focused gate and rollback boundary, and may be left incomplete without claiming the umbrella complete. The FCIS manifest contains a command-family capability matrix and proves every family is reachable from `reef-workflows`; a focused green slice is never promoted to final evidence. If implementation reveals that a family no longer shares the cross-slice invariant, it must move to a separately completable OpenSpec change rather than broadening this umbrella.

Before implementation, stable requirement/scenario/fixture IDs, the command-family matrix, typed vocabularies, prerequisite credential regression edge, exact bounds/projection table, and failing `reef-workflows --slice protocol` runner are registered.

## Risks / Trade-offs

- **Workflow complexity:** migrate one command family at a time over a small closed vocabulary.
- **Large blobs:** content-addressed ownership avoids plan copies but requires explicit lifetime, digest revalidation, and cleanup tests.
- **Host drift:** lock then revalidate prerequisites/blobs before mutation.
- **Transaction regressions:** capture traces and inject failure at each lock/revalidate/stage/verify/commit/cleanup boundary.
- **Conformance scope:** include its decision modules explicitly rather than claiming call-site-only FCIS.
- **Public compatibility:** retain path adapters during migration, but do not count them as pure-core completion while they contain policy-bearing I/O.

## Migration Plan

1. Capture current command, request, mutation, notice, remote-action, and failure traces; add protocol, blob-inspection, plan, transaction, denial, replay, credential, and conformance-snapshot test stubs.
2. Create `chelis-reef-core`, resolved configuration, domain requests/observations, deterministic request identities, explicit audit replay, blob-candidate/core-inspection types, local/remote plan algebras, and the remote-body digest/idempotency encoding; pass `--slice protocol`.
3. Require green evidence from the independent `.venv/bin/python scripts/fcis_gate.py reef-explicit-credentials` oracle and retain its no-fallback/secret-exclusion corpus as regression inputs.
4. Migrate read-only Reef audit/doctor and conformance audit to snapshot/workflow analysis; pass `--slice read-only`.
5. Add whole-local-plan validation and transaction executors with ordered-lock-then-revalidate behavior; migrate fetch/install and pass `--slice local-install`.
6. Migrate conformance init/sync/bump and setup reconciliation with explicit per-artifact/recoverable multi-artifact semantics; pass `--slice conformance`.
7. Migrate source sync/wiring and pass `--slice source-wiring`.
8. Migrate publish to `RemoteActionPlan` with idempotency and indeterminate-state reconciliation; pass `--slice remote-publish`.
9. Remove policy-bearing direct host access after each family passes its focused gate, then run the umbrella acceptance oracle only after every designated family is migrated.

Rollback is command-family scoped and preserves on-disk formats. It must not restore silent credential fallback, ambient blob substitution, unlocked mutation, false global/remote atomicity, or an FCIS completion claim for direct-I/O policy code. Focused gates are supporting evidence and do not replace the final oracle.

## Acceptance Oracle

The authoritative completion oracle is:

```text
.venv/bin/python scripts/fcis_gate.py reef-workflows
```

The runner must execute request/observation correlation and explicit non-secret replay, manifest-configured pinned Dylint plans, positive/negative detector fixtures, and registered disposable fix/no-fix/Reef-conformance-parity/idempotence fixtures for every declared Reef-core/conformance decision lane, no-workflow-cache surface checks, core-issued blob inspection and under-lock revalidation, full local/remote plan validation, canonical lock-set ordering, lock-then-prerequisite revalidation, dry-run, explicit-credential/no-`gh` behavior, capability denial, per-atomicity-unit transaction failure injection, journal recovery, canonical remote-body digest/idempotency golden vectors, indeterminate reconciliation, package security, idempotency, Reef CLI parity, conformance snapshot/planning parity, and structured notice/report fixtures against one revision. Success means exit status 0, an empty reported error list, no host action in denied/replay fixtures, no lock or mutation event in dry run, no complete-success report after partial local or indeterminate remote execution, no digest/idempotency cycle, and no general `ReefQueryKey` or local/workflow plan-cache contract.

## Deferred Follow-ups

- Local-plan or workflow-result serialization and caching remain out of scope until redaction, stable schema, and blob-lifetime guarantees pass the acceptance oracle.
- Notice codes remain internal structured fields unless a separate machine-API compatibility proposal promotes them.
